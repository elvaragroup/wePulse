# Results dashboard — design spec

## Context

The crisis-sim harness (see `CRISIS_SIM_VALIDATION_SPEC.md`) currently exposes results only
as raw JSON files under `runs/<run_id>/` and, once scored, `results/scores.csv` /
`results/report.txt`. Judging whether the personas and the aggregation are behaving
correctly today means manually opening a dozen JSON files and eyeballing them — which is
exactly what was done by hand after the live 2-event smoke test (2026-07-29) to confirm
personas discriminate correctly between a risky announcement and a boring one.

This spec adds a lightweight, read-only HTML dashboard that renders one run's events,
persona reactions, and aggregated arm predictions in a single page, so that judgment call
can be made by scanning a page instead of grepping JSON files.

`CRISIS_SIM_VALIDATION_SPEC.md` §0 lists "No web UI" as an explicit non-goal of the study
itself (alongside no database, no cloud deployment) — that non-goal is about not growing the
*study infrastructure* into a product. A static, self-contained HTML file generated by a
script, with no server process and no new dependency, does not conflict with it: it is a
viewer over files that already exist, in the same spirit as `events_check.py` printing a
human-readable summary of `events.txt`.

## Goals

- Let the user quickly scan every event in a run, see each arm's aggregated top-3
  prediction, and drill into all 30 personas' individual reactions for that event.
- Zero new dependencies, zero server process, zero build step — one script writes one HTML
  file that opens in any browser.
- Reuse existing data models and loaders (`Event`, `Persona`, `PersonaReaction`,
  `ArmPrediction`) rather than introducing new parsing logic.

## Non-goals

- Ground truth, `results/scores.csv` metrics, and leakage verdicts are **not** shown in this
  version — the user explicitly scoped this to reactions + aggregated predictions. These are
  natural follow-ups if wanted later, but out of scope now (YAGNI).
- No cross-run comparison. One `run_id` in, one HTML file out.
- No filtering/search UI. Content is static once generated; re-run the generator if the run
  changes.
- No live server, no auto-refresh.

## CLI

```
uv run python -m src.dashboard <run_id> [--repo PATH] [--out PATH]
```

- `run_id` (positional, required): the run to render, e.g. `20260729T165142.726Z_2ec30ae6`.
- `--repo`: override the repo root (defaults to the module's own repo root, matching
  `run_sim.py`/`score.py`'s `REPO` convention). Exists for testability.
- `--out`: override the output path. Default: `runs/<run_id>/dashboard.html`.

Exits non-zero with a clear message if `runs/<run_id>/manifest.json` does not exist.

## Data sources

All reads go through existing loaders — no new parsing:

| Source | Loader | Fields used |
|---|---|---|
| `inputs/events.txt` | `events.load_events` | `id`, `company`, `headline`, `announcement`, `expected_null` |
| `personas/*.md` | `personas.load_personas` | `id`, `name`, `archetype`, `axis` |
| `runs/<run_id>/raw/B30/<event_id>/<persona_id>.json` | `PersonaReaction.model_validate_json` | `reaction`, `categories`, `intensity`, `quote`, `reasoning` |
| `runs/<run_id>/predictions/<event_id>__<arm>.json` | `ArmPrediction.model_validate_json` | `arm`, `ranked_categories`, `scores`, `backlash_predicted` |

The dashboard always reads from `inputs/events.txt` as it exists *now*, not whatever events
file the run was originally executed against (`--events` overrides aren't recorded anywhere
retrievable). This is a known limitation: if `events.txt` has since changed, headlines shown
could mismatch what the run actually saw. Acceptable for this version since the common case
is dashboard-right-after-run.

## Page structure

Single HTML file, one `<details>` element per event (native expand/collapse, no JS
required for that). Events in file order.

**Collapsed (always visible):**
- Event id, company, headline
- `expected_null` badge
- One line per arm (A, B3, B8, B15, B30, C) present in `runs/<run_id>/predictions/`, showing
  its ranked top-3 and whether it predicted backlash

**Expanded (on click):**
- The full announcement text
- A reaction-mix summary: counts of `ignore` / `mild_concern` / `criticize` / `outrage`
  across all personas found for that event
- A table of personas that did **not** ignore, sorted by `intensity` descending, columns:
  persona id + name, archetype, reaction, categories, intensity, quote
- A collapsed one-line list of persona ids/names that ignored (not a full table row each —
  keeps the expanded view focused on signal)

## Error handling

- Missing `runs/<run_id>/manifest.json` → the script exits with an error before writing
  anything (mirrors `score.py`'s `ScoreError` pattern — a new `DashboardError`).
- An event listed in `events.txt` with no predictions/reactions on disk yet (e.g. a run that
  errored partway through) → that event's card renders with a "not yet run" notice instead of
  crashing the whole generator.
- A persona file that no longer exists for a persona_id found in `raw/B30/<event_id>/`
  (e.g. persona set changed after the run) → fall back to showing the raw persona_id with a
  "(persona file not found)" note rather than raising.

## Testing

Following this codebase's existing pattern (pure functions tested directly, `FakeLLMClient`-
free since no LLM calls are involved here):

- Data-assembly functions (grouping reactions by event, sorting reacted-before-ignored by
  intensity) tested directly against hand-built `PersonaReaction`/`ArmPrediction` fixtures.
- HTML-rendering smoke test: generate a dashboard from fixtures and assert expected content
  appears (event id, persona name, category tag, arm label) in the output string.
- Error-path tests: missing manifest raises `DashboardError`; missing event data renders a
  notice instead of raising; missing persona file renders a fallback instead of raising.
- No browser automation — this is a static-file generator, not an interactive app.

## File

New module: `src/dashboard.py`, following the CLI-script conventions already used by
`run_sim.py` / `score.py` (module-level `REPO`, an `Error` class, a `main()` with
`argparse`). New test file: `tests/test_dashboard.py`.
